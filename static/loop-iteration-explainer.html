Offline Evaluator-Optimizer Loop

这套 loop 不是“AI 评 AI”

它真正干的事，是先用确定性规则把结构、引用、证据和语义硬伤卡死，只有这些都过了，才允许 LLM 做更主观的复核。换句话说：规则先当保安，LLM 后当评委，reflector 当教练。

目标

优化子模块，不改线上默认行为

loop 只在离线 worktree 里注入 prompt/code 变体，用真实 v4 工作流结果来评估哪个变体更好。

核心原则

先硬评估，后主观复核

确定性断言失败时，直接跳过 LLM judge，避免“说得像回事”掩盖结构和事实问题。

结果产物

每一轮都有证据链

最后会落出 report、state、case 结果、变体清单和 promotion 建议，方便人工复盘。

6 状态节点：generate_variant → run_trial → deterministic_eval → llm_judge → reflect → prepare_promotion
2 评估层：确定性规则是主层，LLM judge 是辅层，而且只能压分不能抬分。
0 自动 push / 自动 merge。最佳变体只会写进 run worktree，最终仍需要人工确认。
01 / 主流程

整套 loop 是怎么转起来的

先生成本轮变体，再跑真实工作流拿结果，先做确定性评估；不达标就复盘并生成下一轮约束，达标才允许进入 LLM 复核。整个过程围绕“先卡硬伤，再谈质量”。

Node 1

generate_variant

生成 baseline 或新变体。后续变体会带着上轮 reflector 给出的明确约束。

Node 2

run_trial

拿这个变体去跑真实 v4 工作流，不是假分，不是 mock，直接看真实 target 输出。

Node 3

deterministic_eval

检查结构、数量、ID 引用、explicit ratio、case 级语义标签。这里是主裁判。

Node 4

llm_judge

只有确定性过线后才会进来，负责更主观的忠实度、颗粒度、关系自然度复核。

Node 5

reflect / prepare

不过就 reflect，把失败翻译成下一轮约束；过了就 prepare promotion，保存最佳变体。

最关键的一条

确定性评估没过，LLM 没有发言权。这样就避免了“结构明明错了，但 judge 觉得还行”的盲目通过。

02 / 评估器

评估器分两层，但地位不对等

这套设计不是两个评委平起平坐，而是先过机器质检，再过高级验货。前一层负责“不能错”，后一层才负责“更像好答案”。

第一层 / 主层

Deterministic Eval

用 Promptfoo 或 Python evaluator 做硬断言。这里不看文采，只看结构、引用、证据和语义硬伤。

  • 是不是合法 JSON 对象
  • 数量阈值够不够，比如 value_stream、work_items 最少几个
  • ID 是否自洽，不能引用不存在的 entity / capability / work item
  • explicit evidence ratio 是否达标，避免 inferred 堆满一页
  • 是否命中 hard failure tags，比如缺 AI 中间层、工作事项过粗、value stream 命名失真
第二层 / 辅层

LLM Judge

只有前面过了才会执行。它看的是更主观的质量，比如忠于 JD 原文、颗粒度是否稳、关系是否自然。

  • judge 只能压分，不能抬分
  • 最终分数取 min(确定性分, judge分)
  • 所以一个硬伤结果，没法被“嘴说圆了”洗白
一句人话

为什么它不容易“盲目通过”

因为它先问“你有没有答对格式、证据、引用和结构”，再问“你答得好不好”。前一个问题没过，后一个问题根本不问。

结构错：直接打回 结构过：再看主观质量 双层都过：才可能 promotion

这就是这套 loop 和“让另一个大模型随便点评一下”的本质区别。它先消灭瞎编、乱连、过度概括，再谈优化表达。

03 / 具体例子

拿 element_modeling 跑一遍

这是这套 loop 最典型的应用场景。目标通常是：减少抽象实体、补足 AI 中间层、保证 ID 自洽、提高 explicit 证据占比。

输入现状

baseline 看起来完整，但问题很多

value stream 写成大白话总结句

例如“从需求到上线优化的完整闭环”，听起来完整，但不像稳定业务名称。

AI 中间层缺失

没拆出知识库、Agent 工作流、模型服务这类平台对象。

工作事项过粗

把规划、交付推进、验收测试糊成一个大动作，难以验证。

deterministic_eval 输出

这一轮不会进 LLM judge

  • explicit evidence ratio 0.52 < 0.70
  • work_item WI3 references missing capability CAP7
  • missing_ai_transformation_layer
  • overly_broad_work_item
结构未过线 直接 reflect
reflector 产物

失败原因会被翻成下一轮约束

  • 补出 AI 改造中间层实体，不要只停留在业务流程和产品方案。
  • 把 JD 明确出现但当前缺失的阶段拆成独立 work item。
  • 每个主要实体优先引用 JD 原文，减少 inferred 项。
  • capability_ids 只能引用真实存在的 capability。
新变体效果

第 1 轮结构已经明显变好

explicit ratio 升到 0.76

说明模型不再大量凭空补 inferred 项。

ID 错误被修正

图谱内部引用自洽了，不会出现“连向不存在的节点”。

只剩 naming 类问题

结构过线后，才轮到更细的“命名是否稳”问题。

允许进入 LLM judge
LLM judge 复核

这时候才看“更像不像好答案”

judge 会盯住“忠于 JD 原文、颗粒度是否合理、关系是否自然”。如果 judge 认为 value stream 还是像摘要句，就会继续压分并给出改写建议。

judge 给分 0.81

即便确定性分更高，最终分仍取较小值，不允许 judge 抬分洗白。

suggested_change

把 value_stream_name 改成稳定业务名称，而不是“从 A 到 B”的总结句。

最终结果

第 2 轮达到 promotion 条件

变体改完命名后，结构层过线，judge 也过线，trial 总分高于阈值，controller 就会进入 prepare_promotion。

  • 保存最佳变体到 run worktree
  • 落出 report、state、case_results、variants、PROMOTION
  • 仍然不自动 merge，人工最后拍板

04 / 产物

跑完之后你会看到什么文件

这部分不是附属品，而是证据链。它们把“为什么过、为什么没过、下一轮怎么改”全部拆开留下来。

人工读

report.md

看每一轮变体的总分、回归分、capability 分、失败归因和预算摘要。

机器读

loop_state.json

记录 node_trace、最佳 trial、每轮 case 结果和停止原因，是最完整的状态快照。

逐 case

case_results.jsonl

每个 case 的分数、失败原因、metrics、trace_id、trace_log_path 都会单独留存。

变体清单

variants.json

列出本次实际评估过的 prompt/code 变体，方便回看每轮究竟改了什么。

推广建议

PROMOTION.md

只写“建议推广哪段 delta”，不自动推生产；最后仍需要人工确认。

深挖 trace

logs/{trace_id}.md

如果你想看单个 case 的真实输入、输出和 LLM 响应，最后还是回到 trace 日志里核查。
